## 1. 背景・課題

90年代に流行したデジモン風の携帯育成ゲームへのオマージュとして、Web ブラウザだけで遊べる軽量な育成バトル PWA を作る。
公式エミュレーターやスマホアプリは存在するものの、追加インストールなしで気軽に触れて、かつ他プレイヤーとリアルタイムにバトルできる手段は限られる。
ブラウザ完結・PWA インストール可能・WebSocket リアルタイム対戦の3点を満たすゲームを、個人運用可能なスモールサイズ・低コストで提供することを目指す。

---

## 2. ゴール・目的

| フェーズ | ゴール |
|---------|--------|
| MVP（バトル機能含む） | 1人プレイで卵→アルティメットまでの育成と進化が完結し、オンラインバトルで他プレイヤーと対戦できる |
| 拡張 | 複数クリーチャー管理・進化時お絵描き・CPU 戦・ミニゲーム刷新等の周辺機能を充実 |

**成功基準（MVP）:** GitHub Pages に公開され、シャビと友人がスマホ/PC ブラウザで対戦できる状態。バックエンドの通常運用月額コストが $1 以下に収まる。

---

## 3. スコープ

### 対象範囲

- クリーチャーの育成（ごはん・トレーニング・あそぶ・ねる・成長・進化・死亡）
- 進化のたびのお絵描き機能（64×64 ピクセルアート、SVG 保存）
- 複数クリーチャー管理（最大5体、墓石含む）
- バトルシステム（オンライン WebSocket バトル / CPU 戦）
- セーブデータ管理（IndexedDB 永続化、JSON エクスポート/インポート）
- PWA としてのインストール対応（Service Worker + Manifest）

### 対象外

- ユーザーアカウント・ログイン機能（接続認証は HMAC トークンのみ）
- リアルタイムランキング・リーダーボード
- ゲーム内課金・広告
- ネイティブモバイルアプリ（PWA でカバー）
- 個人情報の収集・分析

## 5. 機能要件

| # | 機能名 | 概要 | 優先度 |
|---|--------|------|--------|
| F-001 | クリーチャー育成 | ごはん・トレーニング・あそぶ・ねるで世話。満腹度/しあわせ度/HP/EXP/atk/def/spd/重さを管理 | Must |
| F-002 | 進化システム | age・level・ステータス条件を満たすと自動進化（タマゴ→ベイビー→チャイルド→アダルト→パーフェクト→アルティメット） | Must |

## 6. 非機能要件

### パフォーマンス

- フロントエンド初回ロード: LCP 2.5s 以下（GitHub Pages + Service Worker キャッシュ）
- WebSocket メッセージ往復: 平均 200ms 以下（東京リージョン運用前提）
- バトル中は 60fps 維持
- バンドルサイズ目標: 初回ロードで gzip 250KB 以下

### セキュリティ

- シークレット管理: AWS SSM Parameter Store（HMAC 鍵）+ `.env`（フロントエンドビルド時注入、`.gitignore` 対象）
- 通信暗号化: HTTPS / WSS（API Gateway 標準）
- 認証: $connect 時の HMAC-SHA256 トークン検証（タイムスタンプ ±60秒、`hmac.Equal` による定数時間比較）
- レート制限: 1接続あたり 60 メッセージ/60秒、超過で `429`
- 異常時自動遮断: CloudWatch Alarm → SNS → Lambda → DynamoDB フラグで接続拒否
- カスタム SVG（ユーザー描画）はエクスポート時に除外し、XSS 経路を増やさない

### 可用性

- 動作環境: 公開はインターネット必須。育成と CPU バトルのみオフラインで継続可能（Service Worker）
- 切断時のフォールバック: 60秒の再接続猶予、超過で残存プレイヤー勝利
- アップタイム目標: 個人運用のためベストエフォート（明示 SLO は設けない）

### 保守性

- フロントエンド・バックエンドのモノレポ管理（型定義・WebSocket メッセージ仕様の整合維持）
- Go バックエンドは Lambda エントリーポイント（`cmd/`）と内部パッケージ（`internal/`）を分離しテスト容易性を確保
- creature データはサーバー側で `json.RawMessage` として透過保持し、スキーマ変更に強い構造

### 拡張性

- 新タイプ・新進化系統は `frontend/src/data/evolutions.ts` の追加で対応可能
- Lambda 同時実行数アカウント上限は 50（個人プロジェクトでは現状十分、必要時クォータ申請）
- DynamoDB は TTL 自動削除でコレクション肥大を防止
- API Gateway WebSocket は単一エンドポイントのみで運用（マルチリージョン非対応）

## 7. 制約条件

### 技術的制約

- 対応ブラウザ: Chrome / Safari / Firefox / Edge の最新2バージョン
- 対応デバイス: デスクトップ・モバイル（iOS/Android Safari 含む PWA インストール）
- 言語・ランタイム: Node.js 20+（フロント）、Go 1.24+（バック）、AWS Lambda `provided.al2023`
- 必須サービス: AWS（API Gateway WebSocket / Lambda / DynamoDB / SSM / SNS / CloudWatch）、GitHub Pages、GitHub Actions
- API Gateway WebSocket メッセージサイズ上限: クライアント→サーバー 32KB / サーバー→クライアント 128KB
- Lambda アカウント同時実行数上限 50（`ReservedConcurrentExecutions` は設定不可）

### 予算・期間制約

- 月額コスト: 通常運用 $1 以下、最悪ケースでも $10 以内に収まること
- 期限: 個人プロジェクトのため明示期限なし

### 法的・規制制約

- 個人情報を一切取得しない（アカウント不要、ログ最小化）
- デジモン公式の意匠・キャラクター名は使用しない（オリジナルタイプ・命名）

## 8. 用語定義

| 用語 | 定義 |
|------|------|
| クリーチャー | プレイヤーが育成する個体。1セーブデータに最大5体（死亡含む） |
| 進化ステージ | タマゴ/ベイビー/チャイルド/アダルト/パーフェクト/アルティメットの6段階 |
| アクティブクリーチャー | 現在操作・時間進行している1体。バトルに自動参加 |
| 墓石 | `isAlive: false` の死亡したクリーチャー。リストに残るが操作不可 |
| ルームコード | バトルマッチング用の6桁英数字（紛らわしい I/O/0/1 を除外） |

> 詳細は `docs/glossary.md` を参照。本書には主要用語のみ記載する。

## 9. リスクと対策

| # | リスク | 影響度 | 発生確率 | 対策 |
|---|-------|-------|---------|------|
| R-001 | 大量接続による AWS 課金爆発 | 高 | 低 | CloudWatch Alarm + 自動遮断（接続 500 / Lambda 10000/h でメンテナンスモード） |
| R-002 | クライアントとサーバーの計算結果ズレ | 高 | 中 | 乱数シード方式 + ターン解決順序の仕様化 + clientVersion チェック |
| R-003 | Service Worker キャッシュで更新が反映されない | 中 | 中 | ビルドハッシュをファイル名に埋め込み、開発時は Application タブで Unregister 運用 |
| R-004 | HMAC シークレット漏洩 | 中 | 低 | クライアント側露出を前提に「スクリプトキディ対策レベル」と割り切り、本格攻撃にはレート制限 + 自動遮断で対応 |
| R-005 | 進化ロジック変更で既存セーブデータが壊れる | 中 | 中 | スキーマ変更時は後方互換を保ち、移行関数（`migrateLegacyData`）で対応 |
| R-006 | ユーザー描画 SVG による XSS | 中 | 低 | カスタム SVG をエクスポート対象から除外、表示は信頼境界内に限定 |
